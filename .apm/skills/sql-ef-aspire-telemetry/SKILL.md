# Aspire telemetry

## Purpose

Get Confirmed evidence (commands per request, repeated statements, slow spans) from the Aspire dashboard data instead of guessing from code. Used by the round trips and query shape skills.

## Rules

- Ask before changing any file. Show the diff, explain it is temporary and say how to revert it.
- Read telemetry only. Never execute resource commands that change state.
- Telemetry can contain sensitive data (SQL text, parameters, connection details). Do not copy it into files, commits or PR descriptions. Quote only the minimum in the report.
- Say clearly which items below were verified on the user's machine and which were not.

## Steps

### 1. Detect Aspire

Look for an AppHost project (`Aspire.AppHost.Sdk`, `DistributedApplication.CreateBuilder`, `apphost.cs` or `apphost.ts`) and for service defaults (`AddServiceDefaults`, `ConfigureOpenTelemetry`). Without Aspire, fall back to `sql-ef-round-trips` with a pasted log.

### 2. Check what is running and what is enabled

If the `aspire` CLI is available, ask the user to start the app (`aspire start`) or confirm it is running, then:

```bash
aspire describe --format Json
aspire otel logs --format Json
aspire otel traces --format Json
aspire otel spans --format Json
```

`aspire otel` is marked as Preview in the documentation, so options may change; run `aspire otel --help` first. If the editor has the Aspire MCP server (`aspire agent mcp`, generated by `aspire agent init`), the equivalent tools are `list_resources`, `list_structured_logs` and `list_traces`.

Look for:

- Spans from the database client (`Npgsql`, SqlClient instrumentation, EF Core) on the endpoint the user is testing. If none: tracing is disabled or the service defaults are missing.
- Structured logs with category `Microsoft.EntityFrameworkCore.Database.Command`. If none: command logging is off.
- Whether the span or log carries the SQL text. If it does not, say so; plan analysis then needs the user to paste the SQL.

### 3. Enable what is missing (with approval)

Options, from least to most invasive. Propose one at a time.

1. **Environment variable on the service in the AppHost** (no change in the service code):

```csharp
builder.AddProject<Projects.Api>("api")
    .WithEnvironment("Logging__LogLevel__Microsoft.EntityFrameworkCore.Database.Command", "Information");
```

2. **Log level in the service `appsettings.Development.json`:**

```json
{
  "Logging": {
    "LogLevel": {
      "Microsoft.EntityFrameworkCore.Database.Command": "Information"
    }
  }
}
```

3. If the Aspire client integration has tracing disabled (`DisableTracing`), propose enabling it only for development.

Not verified in the Aspire documentation: that these log entries reach the dashboard structured logs. They should, because the service defaults export `ILogger` logs through OpenTelemetry, but confirm by reading `aspire otel logs` after the change.

Ask the user to restart the service, exercise the endpoint once, and tell you when done.

### 4. Read and analyze

1. Pick one trace for the endpoint. Count database spans and group repeated statements. Hand over to `sql-ef-round-trips` (N+1, loops) and `sql-ef-query-shape` (columns, joins).
2. List the slowest database spans with duration and statement.
3. Mark findings as Confirmed and reference the trace id, never the raw payload.

### 5. Revert

Remind the user to revert the temporary change, and offer to do it after approval.

## Fallback when the CLI is not available

The dashboard exposes an HTTP telemetry API under `/api/telemetry/` (`logs`, `spans`, `traces`) that returns OTLP JSON. Its authentication and stability are not documented as a public contract, so prefer the CLI or the MCP server, or ask the user to export with `aspire export --output ./diagnostics.zip` and read the files without sharing them.
